# Бриф 06 — Автоопределение Docker Compose из проекта

> Предусловие: выполнены брифы 00–03. Работа в `core/`: определение общее для всех плагинов (PHPStan, Psalm, PHP-CS-Fixer, Phan). Если к моменту реализации сделан бриф 05 (WSL), учитывать новое поле `runMode` вместо `useDocker`.

> **Целевая платформа — только OpenIDE.** Правила те же, что в брифе 00: API проверять по jar'ам OpenIDE и записывать в `docs/api-notes.md`, сетевых запросов не делать, от PHP-плагина (`ru.openide.openphp`) не зависеть.

## Цель

Если проект и так запускается в Docker Compose (свой `docker-compose.yml`, Laravel Sail), пользователю не нужно вручную заполнять сервис, путь в контейнере и команду compose: плагин определяет их из проекта и **предлагает** включить Docker-режим. Без согласия пользователя ничего не включается.

## Что проверено (Docker 29.8 / Compose v2, playground/laravel)

| Факт | Следствие |
|---|---|
| `docker compose config --format json` (в папке проекта) отдаёт **нормализованную** конфигурацию: `include`, `extends`, профили, интерполяция переменных и `COMPOSE_FILE` уже применены. Монтирование: `{"type":"bind","source":"<абсолютный путь на хосте>","target":"/var/www/html"}`, плюс `working_dir`, `image`, `build` | Основной источник. YAML самим не разбирать, если работает CLI |
| `docker compose ps --format json` у запущенных контейнеров: метки `com.docker.compose.project.config_files=<файлы через запятую>`, `com.docker.compose.project.working_dir=<папка>` | Если compose-проект запущен с нестандартными файлами (`-f docker-compose.dev.yml`), их можно узнать из меток и подставить в `composeCommand` |
| `docker compose ps --services --status running` — список запущенных сервисов | Пометить в предложении, запущен ли сервис |
| В OpenIDE есть SnakeYAML: `intellij.libraries.snakeyaml.jar` (`org.yaml.snakeyaml.Yaml`) | Запасной разбор, если `docker` не найден или `config` упал (простые случаи: `services.*.volumes` в коротком и длинном синтаксисе) |

Перед реализацией перепроверить и записать в `docs/api-notes.md`; отдельно — разметку Laravel Sail (`vendor/laravel/sail/stubs/docker-compose.stub` или опубликованный `docker-compose.yml`: сервис `laravel.test`, монтирование `.:/var/www/html`).

## Алгоритм определения — чистая логика, с тестами

Вход: JSON из `docker compose config --format json` (или результат запасного разбора YAML), путь проекта на хосте, путь владельца `vendor/` (рабочая папка инструмента), необязательно — список запущенных сервисов.

1. Для каждого сервиса взять bind-монтирования (`type == "bind"`).
2. Подходит монтирование, у которого `source` — **корень проекта или его предок** (тогда путь в контейнере = `target` + относительный остаток). Монтирования вложенных папок (`./storage:/…`) не считаются.
3. Кандидаты сортировать:
   - сервис, где `working_dir` совпадает с вычисленным путём проекта в контейнере, — выше;
   - в `image` или `build` есть признаки PHP (`php`, `sail`, `laravel`, `fpm`, `cli`) — выше; явно не PHP (`mysql`, `postgres`, `redis`, `nginx`, `node`, `mailpit`, `meilisearch`, `selenium` и т.п.) — ниже, но не исключать;
   - запущенный сервис — выше;
   - имя `laravel.test` (Sail) или `app`/`php`/`php-fpm`/`workspace` — немного выше.
4. Результат: `DockerGuess(service, containerProjectPath, composeCommand, running, confidence)` или список кандидатов, если однозначного лидера нет.
5. `composeCommand`: `docker compose`, плюс `-f <файл>` для каждого нестандартного файла (из меток запущенного контейнера или из `COMPOSE_FILE`, если его видно). Стандартные имена (`compose.yaml`, `compose.yml`, `docker-compose.yml`, `docker-compose.yaml` и `*.override.*`) не добавлять.

Фикстуры для тестов: обычный compose с `./:/var/www/html`; Sail (`laravel.test`, `.:/var/www/html`, mysql/redis рядом); несколько PHP-сервисов (`app`, `queue`, `scheduler`) с одинаковым монтированием; монтирование предка проекта (монорепо); только вложенные монтирования (не подходит); проект без compose.

## Когда и как предлагать

- **При открытии проекта** (`ProjectActivity`, в фоне): если у инструмента режим «локально», бинарник локально **не найден** (или найден, но PHP локально нет — по желанию) и в корне проекта есть compose-файл → определить и показать одно уведомление в группе инструмента:
  > «Похоже, проект работает в Docker Compose: сервис `laravel.test`, путь `/var/www/html`. Запускать PHPStan в контейнере?» [Включить] [Настроить…] [Больше не спрашивать]
  - «Включить» — записать `useDocker`/`runMode = DOCKER`, сервис, путь, команду compose в настройки инструмента и сбросить троттлинг уведомлений; затем перезапустить подсветку открытых файлов.
  - Если сервис не запущен — в тексте так и написать («сервис сейчас не запущен: `docker compose up -d`»).
  - Если кандидатов несколько — «Настроить…» открывает настройки с выбором.
  - Не спрашивать повторно: флаг «больше не спрашивать» на проект (`PropertiesComponent`), и не спрашивать, если Docker-режим уже настроен.
- Если плагинов несколько (PHPStan, Psalm, CS-Fixer), предложение от каждого — отдельное. Объединение в одно общее уведомление — кандидат на потом (нужен общий компонент вне плагинов, а у каждого плагина своя копия `core`).
- **В настройках** (`ToolConfigurable`) рядом с полями Docker — кнопка «Определить из docker-compose»: запускает определение в фоне с прогрессом, заполняет поля рабочей копии (как «Проверить»), при нескольких кандидатах — выпадающий список; затем можно сразу нажать «Проверить».
- Если `docker` не найден — запасной разбор YAML и пометка «не удалось проверить через docker CLI».

## Проверка кандидата (по желанию, только для запущенного сервиса)

`docker compose exec -T -w <путь> <сервис> test -x <vendor/bin/tool>` — инструмент действительно есть в контейнере. Если нет — в уведомлении: «в контейнере не найден vendor/bin/phpstan».

## Тесты (JUnit, без платформы)

- Выбор сервиса и пути на фикстурах `docker compose config --format json` (см. выше), включая монтирование предка проекта и Windows-пути хоста (`C:\…` — сравнение без учёта регистра и разделителей).
- Сборка `composeCommand` из меток `config_files` (стандартные и нестандартные имена).
- Запасной разбор YAML: короткий (`./:/var/www/html`, `.:/var/www/html:cached`) и длинный синтаксис `volumes`.
- Логика «предлагать / не предлагать» как чистая функция от состояния (режим, найден ли бинарник, флаг «не спрашивать», есть ли compose).

## Ручная проверка (playground/laravel)

1. Сбросить настройки PHPStan, удалить локальный `vendor/bin/phpstan` из PATH-поиска (или переименовать временно) — при открытии проекта предложение «запускать в контейнере `app`, `/var/www/html`»; «Включить» — подсветка работает через Docker.
2. Остановить контейнер — предложение пишет, что сервис не запущен.
3. Кнопка «Определить из docker-compose» в настройках заполняет поля; «Проверить» показывает версию из контейнера.
4. Compose с `-f docker-compose.dev.yml` (запущенный) — в команде compose появляется `-f`.
5. Sail-проект (`laravel.test`) — определяется без вопросов о выборе сервиса.
6. Проект без compose — никаких предложений.

## Не делать

- Не включать Docker-режим без согласия пользователя.
- Не брать настройки Docker/Compose-интерпретатора из PHP-плагина OpenIDE (внутреннее состояние, может уйти за пэйвол).
- Не запускать `docker compose up` и вообще не менять состояние контейнеров.
- Не править compose-файлы пользователя.
