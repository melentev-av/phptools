# Бриф 05 — Запуск инструментов в WSL

> Предусловие: выполнены брифы 00–03 (общий `core`, плагины PHPStan, Psalm, PHP-CS-Fixer). Работа почти целиком в `core/`: режим запуска общий, поэтому WSL сразу появится во всех плагинах (и в Phan из брифа 04).

> **Целевая платформа — только OpenIDE.** Правила те же, что в брифе 00: API проверять по jar'ам OpenIDE и записывать в `docs/api-notes.md`, сетевых запросов не делать, от PHP-плагина (`ru.openide.openphp`) не зависеть.

## Цель

Плагины работают, когда OpenIDE запущена на **Windows**, а проект и PHP — **внутри WSL** (типичный Laravel на Windows): проект открыт по пути `\\wsl$\Ubuntu\home\user\app` или `\\wsl.localhost\Ubuntu\home\user\app`, а `php`, Composer и `vendor/` есть только в Linux.

## Что сейчас

| Сценарий | Статус |
|---|---|
| Windows, проект на диске Windows, PHP для Windows | Должно работать (локальный режим, `.bat` учитывается); не проверено |
| Windows, Docker Desktop (в т.ч. на WSL2) | Должно работать (Docker-режим вызывает `docker compose` из Windows); не проверено |
| **Windows, проект и PHP внутри WSL** | **Не работает**: плагин запускает `vendor/bin/<tool>` как программу Windows и передаёт Windows-пути |

## Режим запуска «WSL»

Третий режим рядом с «локально» и «Docker Compose». По устройству — как Docker: команда выполняется «где-то ещё», пути переводятся туда и обратно.

### Настройки (изменение `ToolState` в `core`)

Вместо флага `useDocker` — перечисление режима, с миграцией старых настроек.

| Поле | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `runMode` | enum `LOCAL` / `DOCKER` / `WSL` | `LOCAL` | Режим запуска. Миграция: `useDocker = true` → `DOCKER` (старое поле читать при загрузке и больше не писать) |
| `wslDistribution` | String | `""` | Имя дистрибутива (`Ubuntu-24.04`). Пусто — из пути проекта (`\\wsl$\<имя>\…`), иначе дистрибутив по умолчанию |
| `wslLoginShell` | Boolean | `false` | Запускать через `bash -lc` (если `php` доступен только после `.bashrc`/`.profile`: asdf, phpenv, Herd и т.п.) |

В `ToolConfigurable` — радиокнопки «Запуск: локально / Docker Compose / WSL»; для WSL — выпадающий список дистрибутивов (`WslDistributionManager.getInstance().getInstalledDistributions()`, **только на Windows**; на других ОС пункт WSL скрыт) и чекбокс login shell.

Если проект открыт по WSL-пути, а режим `LOCAL`, — при открытии проекта (или в полосе над настройками) предложить переключиться на WSL.

### Сборка команды — чистая логика в `LaunchPlan`, с тестами

```
wsl.exe -d <distro> --cd <linuxWorkDir> --exec [php] <exe> args...                 # обычный запуск
wsl.exe -d <distro> --cd <linuxWorkDir> --exec bash -lc '<quoted command>'          # wslLoginShell
wsl.exe -d <distro> --cd <linuxWorkDir> --exec sh -c '<TEMP_FILE_SCRIPT>' sh /tmp/phptools-<uuid>.<ext> [php] <exe> args...   # runWithTempFile
```

- `--exec` — без промежуточной оболочки: аргументы передаются как есть, без экранирования.
- Для `bash -lc` команда собирается в одну строку с POSIX-экранированием каждого аргумента (`'…'`, внутренняя `'` → `'\''`); экранирование — чистая функция с тестами.
- Временный файл для несохранённого буфера (PHPStan `--tmp-file`) создаётся **внутри WSL** тем же `sh -c`-скриптом, что и в Docker (`LaunchPlan.TEMP_FILE_SCRIPT`), на хосте ничего не пишется.
- stdin (PHP-CS-Fixer `fix -`) передаётся через `wsl.exe` как есть.
- Локальная рабочая папка процесса — любая существующая папка Windows (например, `%USERPROFILE%`): cwd внутри WSL задаёт `--cd`. Не использовать UNC-путь проекта как cwd процесса Windows.

### Маппинг путей — чистая логика, с тестами

- Windows → WSL:
  - `\\wsl$\<distro>\home\u\app\x.php`, `\\wsl.localhost\<distro>\…` и те же пути с прямыми слэшами (`//wsl$/…` — так их часто хранит `project.basePath`) → `/home/u/app/x.php`;
  - путь на диске Windows `C:\Users\u\x.php` → `/mnt/c/Users/u/x.php` (корень монтирования по умолчанию `/mnt/`; если понадобится — настройка);
  - сравнение имени дистрибутива — без учёта регистра.
- WSL → Windows (вывод инструментов, отчёт панели): `/home/u/app/x.php` → `\\wsl.localhost\<distro>\home\u\app\x.php` (тот же префикс, что у пути проекта), `/mnt/c/…` → `C:\…`.
- Можно сверить результат с `WslPath.parseWindowsUncPath` / `WSLDistribution.getWslPath(Path)` / `getWindowsPath(String)` (без пометок `@Internal` в 262), но основная логика — своя, как в `LaunchPlan` для Docker.

### Поиск бинарника

`BinaryResolver` уже работает по UNC-путям: `\\wsl$\…\vendor\bin\phpstan` виден из Windows как обычный файл. В режиме WSL найденный путь переводится в Linux-путь (как для Docker). Windows-специфику (`.bat`) в режиме WSL не применять.

## Что проверить при реализации (на Windows)

Перед реализацией и по ходу — проверить на реальной Windows с WSL2 и записать в `docs/api-notes.md`:

1. Как `project.basePath` выглядит для проекта в WSL (`//wsl$/…`, `//wsl.localhost/…` или иначе).
2. **Кодировка вывода `wsl.exe`.** Вывод запущенной программы проходит как есть (UTF-8), но собственные сообщения `wsl.exe` (например, «дистрибутив не найден») приходят в UTF-16LE. Распознавать по нулевым байтам и декодировать, чтобы уведомление было читаемым.
3. Какой `PATH` у `--exec` без оболочки — находится ли `php` из пакетов дистрибутива (ожидаемо да), из asdf/phpenv (ожидаемо нет → `wslLoginShell`).
4. Скорость: накладные расходы `wsl.exe` на каждый запуск (ожидаемо десятки–сотни мс); при «холодном» дистрибутиве первый запуск дольше — таймауты не должны срабатывать.
5. Отмена: убивает ли отмена индикатора процесс внутри WSL, а не только `wsl.exe` (если нет — завершать через `wsl.exe -d <distro> --exec kill`, либо документировать).
6. Docker в WSL (`docker` есть только внутри Linux): работает ли Docker-режим с `composeCommand = wsl.exe -d <distro> docker compose` — если да, описать в README как рецепт.

## Тесты (JUnit, без платформы)

- Маппинг путей: `\\wsl$\…`, `\\wsl.localhost\…`, `//wsl$/…`, регистр имени дистрибутива, `C:\…` ↔ `/mnt/c/…`, путь вне проекта, обратный маппинг для отчёта.
- Сборка команд: обычный запуск, с PHP-интерпретатором, login shell (экранирование кавычек, пробелов, `$`), `runWithTempFile`, stdin-сценарий PHP-CS-Fixer.
- Миграция настроек `useDocker` → `runMode`.
- Регресс: все существующие тесты локального и Docker-режима проходят без изменений.

## Ручная проверка (Windows + WSL2, делает тестировщик)

В WSL: Laravel-проект с PHPStan, Psalm и PHP-CS-Fixer в `vendor/`, проект открыт в OpenIDE по пути `\\wsl.localhost\<distro>\…`.

1. При открытии проекта — предложение переключиться на WSL.
2. Settings → Tools → PHPStan → режим WSL, дистрибутив из списка → «Проверить» показывает версию PHPStan из WSL.
3. Подсветка PHPStan в несохранённом файле (временный файл внутри WSL).
4. Psalm: подсветка после сохранения; колонки верные при кириллице.
5. PHP-CS-Fixer: подсветка через stdin, «Исправить через PHP-CS-Fixer» на папке — файлы в WSL исправлены, редактор показывает новое содержимое.
6. Панель любого плагина: «Проверить проект», в отчёте пути — Windows-пути WSL, переход к коду работает.
7. Неверное имя дистрибутива — одно понятное уведомление (не «кракозябры» UTF-16).
8. php только через asdf/phpenv — без login shell понятная ошибка, с `wslLoginShell` работает.
9. macOS/Linux: пункта WSL в настройках нет, всё работает как раньше.

## Не делать

- Не зависеть от PHP-интерпретаторов PHP-плагина OpenIDE (`ru.openide.openphp`, в т.ч. `PhpToolLaunch` с поддержкой WSL): может уйти за пэйвол.
- Не использовать `WSLDistribution.patchCommandLine(…, String, boolean)` (`@Internal` + `@Deprecated` в 262) и `getUNCRootPath()` (`@Experimental`).
- Не копировать файлы проекта между Windows и WSL.
- Не включать WSL-режим автоматически без согласия пользователя.
